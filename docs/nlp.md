# トークナイザと埋め込み

「インタラクティブ1（ことばを数字にする）」の中身です。3 つの選択が独立しています。

```
入力文 ──① トークナイザ──▶ トークン列 ──② 埋め込み──▶ ベクトル
                                                   ├─▶ ヒートマップ / PCA 2D
                                                   └─▶ ③ 近傍プールとの類似度
```

| 選択 | 設定名 | 値 |
| --- | --- | --- |
| ① 分割 | `tokenizerMode` | `gpt` / `llmjp` / `ruri` |
| ② ベクトル化 | `embeddingSource` | `openai` / `ruri`（+ `ruriSize`） |
| ③ 近いことばを探す対象 | `neighbourSource` | `curated` / `tokenizer` / `llmjp` |

**①と②は互いに独立です。** 受け渡しはトークン ID ではなく**文字列**なので、
どの組み合わせでも動きます（[Interactive1Step.tsx](../src/player/Interactive1Step.tsx) の `tokens.map(t => t.text)`）。

## ① トークナイザ

| モード | 実装 | 語彙 | 由来 |
| --- | --- | --- | --- |
| `gpt` | [lib/tokenizer.ts](../src/lib/tokenizer.ts) | o200k_base | js-tiktoken（BPE）。GPT-4o の実物 |
| `llmjp` | [lib/llmjp.ts](../src/lib/llmjp.ts) | 99,574 | llm-jp/llm-jp-3-1.8b の SentencePiece Unigram |
| `ruri` | [electron/localEmbed.ts](../electron/localEmbed.ts) | 102,400 | Ruri v3 が内部で使うもの。ModernBERT-Ja 経由の Sarashina2 由来 |

同じ文でも切れ方が違うことを見せるのが展示の狙いです。

```
GPT-4o  : [大][規][模][言][語][モデル][は][次][の][単][語][を][予][測][する]  15個
llm-jp  : [大規模][言語][モデル][は][次][の][単語][を][予測][する]            10個
Ruri v3 : [大規模][言語][モデル][は次の][単語][を予測する]                     6個
```

### llm-jp は自前の Viterbi

語彙とスコアだけを `src/content/llmjp-vocab.json` に持ち、**Unigram の最適分割を自前で解いています**。
Unigram は「語彙に含まれる断片へ分割したときのスコア合計が最大になる切り方」を選ぶ方式なので、
動的計画法で解けば本家と同じ結果になります。ライブラリを足さずにレンダラだけで完結させるための実装です。

語彙ファイルの生成は `node scripts/build-llmjp-vocab.mjs`（Hugging Face から取得して整形）。

### Ruri のトークナイザはメインプロセス側

Ruri の語彙は 7MB 弱の `tokenizer.json` で、ダウンロードが要るのでレンダラでは扱いません。
`local:tokenize` 越しに呼びます。**モデル本体（35〜300MB）は落とさずトークナイザだけ**読むよう、
`getTokenizer()` を `getPipeline()` から分離してあります。

語彙外の文字は `<0xNN>` のバイトトークンに落ちるので、**連続するバイトトークンはまとめて
文字に戻してから**返します（画面に `<0xE3>` と出ては展示になりません）。

### 分割位置は埋め込みと一致するとは限らない

`gpt` や `llmjp` を選んだ場合、**画面に見せている区切りと、Ruri が内部で使う区切りは一致しません**。
llm-jp と Ruri の語彙は 42% しか重ならず、同じ ID に同じ文字列が入っているのは 102,400 個中 5 個だけです。

```
"ドラゴンボール"      画面: [ドラゴン][ボール]        Ruri 内部: [ドラゴンボール]
"カピバラがかわいい"  画面: [カピバラ][が][かわいい]  Ruri 内部: [カ][ピ][バラ][がかわいい]
```

壊れはしません（Ruri は受け取った文字列を自分で切り直すため）が、説明としてはズレます。
揃えたいときは `tokenizerMode` を `ruri` にしてください。

## ② 埋め込み

| source | 実装 | 特徴 |
| --- | --- | --- |
| `openai` | [electron/openai.ts](../electron/openai.ts) | `text-embedding-3-*`。256 次元に落として使う。要 APIキー |
| `ruri` | [electron/localEmbed.ts](../electron/localEmbed.ts) | ローカル。APIキー不要・通信なし・数千語でも数秒 |

### Ruri v3 の呼び出し

- 重みは `onnx-community/ruri-v3-*-ONNX`（量子化 ONNX、`dtype: 'q8'`）
- トークナイザは本家 `cl-nagoya/ruri-v3-*`（ONNX 側のリポジトリには入っていない）
- 初回利用時に Hugging Face から取得し、`userData/models` に置く。設定画面から事前ダウンロードできる
- サイズは 30m / 130m / 310m。既定は 130m

処理の順序が結果に効きます。

1. **接頭辞 `トピック: ` を付ける。** Ruri v3 は用途別の接頭辞を前提に学習されています
2. 256 件ずつに分けて推論（パディングが最長文に引きずられないように）
3. **平均プーリング。** `attention_mask` が 0 の位置は平均に含めません
4. L2 正規化

### 接頭辞の希釈と中心化

1 トークンだけを埋め込むと、平均プーリングの対象 6 個のうち**中身は 1 個（17%）**しかありません
（`トピック: ` が 3 トークン、`<s></s>` が 2 個）。放っておくと全ベクトルが接頭辞の方向に偏り、
コサイン類似度が軒並み 0.9 台に張り付きます。

そこで **`embeddingSource === 'ruri'` のときだけ、プール全体の平均ベクトルを引いてから**
比較しています（`centerVec` / `meanVector`）。表示側でも最大値で正規化しています。
**この 2 つは飾りではなく、この構成では必須の補正です。**

## ③ 近傍プール

| source | 語数 | 中身 |
| --- | --- | --- |
| `curated` | 約 120 | [src/content/vocabulary.ts](../src/content/vocabulary.ts) の厳選語彙。結果が読みやすい |
| `tokenizer` | 1,842 | o200k_base から抽出した日本語 |
| `llmjp` | 数万 | llm-jp の語彙から抽出した日本語 |

`tokenizer` の抽出条件は「かなを含む」または「常用漢字のみ（2文字以上）」です。
常用漢字の縛りで簡体字の中国語はほぼ落ちますが、**日本語と共通の漢字だけで書かれた
中国語スパム（賭博・アダルト系）はすり抜ける**ので、語幹のブラックリスト（`SPAM_STEMS`）で
落としています。高校生に見せる展示なので安全側に倒した処理です。

それでも `天天` `提款` や 5ch 由来の語は残ります。**来場者に見せる前に一度自分で試してください。**

## キャッシュ

プールの埋め込みは語数が多く取得が重いので、二段構えでキャッシュします。

1. メモリ（`poolMemo`。ウィンドウを閉じるまで）
2. ディスク（`userData/cache`。[data.md](data.md) にキー形式）

ディスクキャッシュは「語数が一致し、先頭の語も一致する」ときだけ使うので、語彙を変えれば
自然に作り直されます。

## オフライン時の縮退

展示中にネットワークが切れても止まらないようにしてあります。

| 失敗した処理 | 縮退 |
| --- | --- |
| トークナイザの読み込み | o200k_base（バンドル済み）にフォールバック |
| 埋め込みの取得 | `pseudoEmbed()` の決定的な疑似ベクトル。**プールと入力の両方を疑似に揃える** |
| 次トークン候補（interactive2） | 語尾のパターンから作る簡易候補 |

疑似ベクトルに落ちたときは画面に明示します。**実埋め込みと疑似ベクトルを混ぜると比較が
成立しない**ので、プール側が疑似なら入力側も必ず疑似にします。

分割がフォールバックした場合、画面のラベルも実際に使ったトークナイザの名前に変わります
（`usedMode`）。設定と表示が食い違わないようにするためです。
