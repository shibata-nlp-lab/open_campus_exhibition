# トークナイザと埋め込み

「インタラクティブ1（ことばを数字にする）」の中身です。3 つの選択が独立しています。

```
入力文 ──① トークナイザ──▶ トークン列 ──② 埋め込み──▶ ベクトル
                                                   ├─▶ ヒートマップ / PCA 2D
                                                   └─▶ ③ 近傍プールとの類似度
```

| 選択 | 設定名 | 値 |
| --- | --- | --- |
| ① 分割 | `tokenizerMode` | `gpt` / `llmjp` / `ruri` |
| ② ベクトル化 | `embeddingSource` | `openai` / `ruri`（+ `ruriSize`）/ `llmjp`（+ `llmjpSize`） |
| ③ 近いことばを探す対象 | `neighbourSource` | `curated` / `tokenizer` / `llmjp` |

**①と②は互いに独立です。** 受け渡しはトークン ID ではなく**文字列**なので、
どの組み合わせでも動きます（[Interactive1Step.tsx](../src/player/Interactive1Step.tsx) の `tokens.map(t => t.text)`）。

## ① トークナイザ

| モード | 実装 | 語彙 | 由来 |
| --- | --- | --- | --- |
| `gpt` | [lib/tokenizer.ts](../src/lib/tokenizer.ts) | o200k_base | js-tiktoken（BPE）。GPT-4o の実物 |
| `llmjp` | [lib/llmjp.ts](../src/lib/llmjp.ts) | 99,574 | llm-jp/llm-jp-3-1.8b の SentencePiece Unigram |
| `ruri` | [electron/localEmbed.ts](../electron/localEmbed.ts) | 102,400 | Ruri v3 が内部で使うもの。ModernBERT-Ja 経由の Sarashina2 由来 |

同じ文でも切れ方が違うことを見せるのが展示の狙いです。

```
GPT-4o  : [大][規][模][言][語][モデル][は][次][の][単][語][を][予][測][する]  15個
llm-jp  : [大規模][言語][モデル][は][次][の][単語][を][予測][する]            10個
Ruri v3 : [大規模][言語][モデル][は次の][単語][を予測する]                     6個
```

### llm-jp は自前の Viterbi

語彙とスコアだけを `src/content/llmjp-vocab.json` に持ち、**Unigram の最適分割を自前で解いています**。
Unigram は「語彙に含まれる断片へ分割したときのスコア合計が最大になる切り方」を選ぶ方式なので、
動的計画法で解けば本家と同じ結果になります。ライブラリを足さずにレンダラだけで完結させるための実装です。

語彙ファイルの生成は `node scripts/build-llmjp-vocab.mjs`（Hugging Face から取得して整形）。

### Ruri のトークナイザはメインプロセス側

Ruri の語彙は 7MB 弱の `tokenizer.json` で、ダウンロードが要るのでレンダラでは扱いません。
`local:tokenize` 越しに呼びます。**モデル本体（35〜300MB）は落とさずトークナイザだけ**読むよう、
`getTokenizer()` を `getPipeline()` から分離してあります。

語彙外の文字は `<0xNN>` のバイトトークンに落ちるので、**連続するバイトトークンはまとめて
文字に戻してから**返します（画面に `<0xE3>` と出ては展示になりません）。

### 分割位置は埋め込みと一致するとは限らない

`gpt` や `llmjp` を選んだ場合、**画面に見せている区切りと、Ruri が内部で使う区切りは一致しません**。
llm-jp と Ruri の語彙は 42% しか重ならず、同じ ID に同じ文字列が入っているのは 102,400 個中 5 個だけです。

```
"ドラゴンボール"      画面: [ドラゴン][ボール]        Ruri 内部: [ドラゴンボール]
"カピバラがかわいい"  画面: [カピバラ][が][かわいい]  Ruri 内部: [カ][ピ][バラ][がかわいい]
```

壊れはしません（Ruri は受け取った文字列を自分で切り直すため）が、説明としてはズレます。
揃えたいときは `tokenizerMode` を `ruri` にしてください。

## ② 埋め込み

| source | 実装 | 特徴 |
| --- | --- | --- |
| `openai` | [electron/openai.ts](../electron/openai.ts) | `text-embedding-3-*`。256 次元に落として使う。要 APIキー |
| `ruri` | [electron/localEmbed.ts](../electron/localEmbed.ts) | ローカル。APIキー不要・通信なし・数千語でも数秒 |
| `llmjp` | [electron/llmjpEmbed.ts](../electron/llmjpEmbed.ts) | llm-jp の**埋め込み層そのもの**。モデルを動かさず表を引くだけ |

### Ruri v3 の呼び出し

- 重みは `onnx-community/ruri-v3-*-ONNX`（量子化 ONNX、`dtype: 'q8'`）
- トークナイザは本家 `cl-nagoya/ruri-v3-*`（ONNX 側のリポジトリには入っていない）
- 初回利用時に Hugging Face から取得し、`userData/models` に置く。設定画面から事前ダウンロードできる
- サイズは 30m / 130m / 310m。既定は 130m

処理の順序が結果に効きます。

1. **接頭辞 `トピック: ` を付ける。** Ruri v3 は用途別の接頭辞を前提に学習されています
2. 256 件ずつに分けて推論（パディングが最長文に引きずられないように）
3. **平均プーリング。** `attention_mask` が 0 の位置は平均に含めません
4. L2 正規化

### 接頭辞の希釈と中心化

1 トークンだけを埋め込むと、平均プーリングの対象 6 個のうち**中身は 1 個（17%）**しかありません
（`トピック: ` が 3 トークン、`<s></s>` が 2 個）。放っておくと全ベクトルが接頭辞の方向に偏り、
コサイン類似度が軒並み 0.9 台に張り付きます。

そこで **ローカルモデル（`ruri` / `llmjp`）のときは、プール全体の平均ベクトルを引いてから**
比較しています（`centerVec` / `meanVector`）。表示側でも最大値で正規化しています。
**この 2 つは飾りではなく、この構成では必須の補正です。**

## ②-2 llm-jp の埋め込み層

`ruri` / `openai` が「文を読んで意味ベクトルを作るモデル」なのに対し、これは
**LLM がトークンIDを最初にベクトルへ変換する表**（`model.embed_tokens.weight`）そのものです。
文脈は一切入りません。ID で行を引くだけです。

`tokenizerMode: llmjp` と組み合わせると、**画面に出ているトークンIDが、そのまま表の行番号**に
なります。「この数字で表を引くとベクトルが出てくる」という説明がそのまま成立し、
分割位置の食い違い（上記）も原理的に起きません。

### 必要な部分だけ落とす

モデル全体は 1.8b で 3.7GB ありますが、埋め込み層だけなら HTTP Range で抜けます。

1. 先頭 8 バイト（u64 LE）でヘッダ長を読む
2. 続く JSON ヘッダから `model.embed_tokens.weight` の `data_offsets` を得る
3. **絶対位置 = 8 + headerLen + offset** の範囲を 1 回の GET で取る

> **3 の計算を間違えても「それらしい」結果が出ます。** 実装中に headerLen を足し忘れて
> 12,424 バイトずれた状態で近傍を測ったところ、`学校 → 学区` `未来 → 未だ` のように
> 一見「表記が近い語」が並び、壊れているとは見えませんでした。
> [test/safetensors.test.ts](../test/safetensors.test.ts) でこの計算を固定しています。

落としたスライスは加工せずそのまま置き、`行 = トークンID` の位置から必要な分だけ読みます
（1行 = 次元 × 2 バイトの bf16）。量子化も前処理もしません。

| サイズ | 取得量 | 次元 |
| --- | --- | --- |
| `150m`（既定） | 97MB | 512 |
| `440m` | 195MB | 1024 |
| `1.8b` | 389MB | 2048 |

**大きいほど良いわけではありません。** 手元で測った近傍は次のとおりで、
1.8b は「みらい／ミライ」のような表記ゆれを、150m は類義語・上位下位語を返します。

```
150m : 学校 → 中学校 小学校 高校    未来 → 将来 近未来 次世代
1.8b : 学校 → がっこう 校長 授業     未来 → みらい ミライ 近未来
```

複数トークンに割れる語（「トレーニング」など）は、各トークンの行を**平均**して L2 正規化します。
分割はレンダラ側（語彙ファイルがそこにあるため）で行い、メインプロセスには
**トークンIDだけ**を渡します。

## ②-3 次トークンの確率（体験②）

「次に来ることば」の候補と確率は 2 通りで出せます（`Interactive2Content.predictSource`）。

| source | 中身 | 通信 | 速さ |
| --- | --- | --- | --- |
| `openai` | Chat Completions の `top_logprobs` | **要**（APIキーも） | 回線次第 |
| `llmjp` | llm-jp-3 をこの PC で動かす | 不要（初回の取得だけ） | 1手 0.05〜0.5 秒（サイズによる） |

`llmjp` は [electron/llmjpNext.ts](../electron/llmjpNext.ts)。
**②-2 の「埋め込み層」とは別物です。** あちらは表を引くだけですが、こちらは
モデル本体（`AutoModelForCausalLM`）を forward させて、最後の位置のロジットを softmax します。

サイズは 3 つから選べます（`llmjpNextSize`）。いずれも量子化 ONNX（dtype `q8`）で、
下の数値は手元（Apple Silicon / CPU）の実測です。

| size | repo | 取得 | 1手 | `日本の首都は` | `…次の単語を` |
| --- | --- | --- | --- | --- | --- |
| `150m` | `onnx-community/llm-jp-3-150m-instruct3-ONNX` | 153MB | 0.05〜0.1s | 東京 57% | 含む・生成・学習 |
| `440m` | `junhongwang/llm-jp-3-440m-instruct2` | 448MB | 0.1s | 東京 45% | 含む・使用・生成 |
| `980m` | `junhongwang/llm-jp-3-980m-instruct3` | 991MB | 0.2〜0.5s | 東京 **77%** | **生成 23%**・予測 6% |

大きいほど候補は納得しやすくなりますが、待ち時間とダウンロードが増えます。
サイズを切り替えると前のモデルは捨てて読み直します（980m は 1GB 近いので抱えたままにしません）。
読み直しは取得済みなら 1 秒ほどです。

- **先頭に BOS（`<s>`）を必ず付けます。** これで分布がはっきりします
  （手元の計測：`日本の首都は` → 東京 **57.2%**／BOS なしだと 1.9% で、説明になりません）
- 特殊トークン（`<s>` `</s>` `<EOD|LLM-jp>` など、`all_special_ids` の 0..7）は候補から外します。
  `decode()` すると `"<s>"` という文字列がそのまま画面に出てしまうためです
- 候補の並べ替えと絞り込みは [electron/nextTokenPick.ts](../electron/nextTokenPick.ts) に切り出して
  テストしています（モデルなしで試せます）

**確率は softmax したそのままの値で、捨てた分を配り直しません。**
「上位5つを足しても 100% にならない」ことが、次の語が広く散らばっているという説明そのものだからです
（手元の計測：`日本の首都は` は上位5つで 73%、`今日はオープンキャンパスに来て` は 20%）。

初回はモデルの読み込みが入るので（取得済みなら 1 秒ほど、未取得ならダウンロード）、
入力画面を出した時点で先に読み込みを始めます。
設定画面には**選んだサイズの**事前ダウンロードのボタンがあります（サイズごとに別のファイルです）。

## ③ 近傍プール

| source | 語数 | 中身 |
| --- | --- | --- |
| `curated` | 約 120 | [src/content/vocabulary.ts](../src/content/vocabulary.ts) の厳選語彙。結果が読みやすい |
| `tokenizer` | 1,842 | o200k_base から抽出した日本語 |
| `llmjp` | 6,000 | llm-jp の語彙から、日本語判定を通してスコア上位を取ったもの |

`tokenizer` の抽出条件は「かなを含む」または「常用漢字のみ（2文字以上）」です。
常用漢字の縛りで簡体字の中国語はほぼ落ちますが、**日本語と共通の漢字だけで書かれた
中国語スパム（賭博・アダルト系）はすり抜ける**ので、語幹のブラックリスト（`SPAM_STEMS`）で
落としています。高校生に見せる展示なので安全側に倒した処理です。

それでも `天天` `提款` や 5ch 由来の語は残ります。**来場者に見せる前に一度自分で試してください。**

## キャッシュ

プールの埋め込みは語数が多く取得が重いので、二段構えでキャッシュします。

1. メモリ（`poolMemo`。ウィンドウを閉じるまで）
2. ディスク（`userData/cache`。[data.md](data.md) にキー形式）

ディスクキャッシュは「語数が一致し、先頭の語も一致する」ときだけ使うので、語彙を変えれば
自然に作り直されます。保存時は小数4桁に丸めます（順位は変わらず、容量が数分の一になります）。

> **プールの語数には上限（6,000）があります。** llm-jp の語彙は条件を満たすものが 26,000 以上
> ありますが、全部の埋め込みを持つとキャッシュが 260MB 規模の JSON になり、書き出しで画面が
> 止まります。展示で見せるのは上位数語なので、Unigram スコアの高い順に絞っています
> （語彙ファイルの並び順は頻度順ではなく、先頭は `一一` `一二` … です）。

## オフライン時の縮退

展示中にネットワークが切れても止まらないようにしてあります。

| 失敗した処理 | 縮退 |
| --- | --- |
| トークナイザの読み込み | o200k_base（バンドル済み）にフォールバック |
| 埋め込みの取得 | `pseudoEmbed()` の決定的な疑似ベクトル。**プールと入力の両方を疑似に揃える** |
| 次トークン候補（interactive2） | 語尾のパターンから作る簡易候補 |

疑似ベクトルに落ちたときは画面に明示します。**実埋め込みと疑似ベクトルを混ぜると比較が
成立しない**ので、プール側が疑似なら入力側も必ず疑似にします。

分割がフォールバックした場合、画面のラベルも実際に使ったトークナイザの名前に変わります
（`usedMode`）。設定と表示が食い違わないようにするためです。
